## What makes it "incremental"

A change belongs in 0.6.3-alpha only if all of these hold:

- **No new module API.** Modules stay on API 3 and `maxServer: 0.6.x` keeps covering this server. No module has to be re-released because of the server.
- **No database migration that can't be rolled back** by a 0.6.0-alpha server reading the same data folder. A new column is fine if 0.6.0 ignores it; a renamed or dropped table isn't.
- **No new library type, no new page**, and no change to the client API's existing answers. New optional fields are fine; `apiRevision` only moves if a field is added.
- **Each fix is small enough to review in one sitting**, has a test where a test can show it, and is in the changelog in plain words.
- **About 15 UI fixes at most.** The rest of the list rolls to 0.7.0-alpha.

## Top priority: install and run with Windows Smart App Control on

The owner, 2026-11-02: Windows flags the app and says Smart App Control must be turned off; **the installer fails too**, and with it off everything installs and works. Turning it off can't be undone without reinstalling Windows, so no user should be asked to. This is the most important item in 0.6.3-alpha, and the one exception to "small": it touches every repository's release workflow, but changes no product behaviour.

- Sign every Windows program, DLL, script and installer we ship with a trusted code-signing certificate, in CI: [../design/code-signing-pipeline.md](../design/code-signing-pipeline.md).
- Sign the pinned FFmpeg; build game cores ourselves, pinned and signed (WittyPlayCores), because every core from the nightly build server would be blocked.
- Detect Smart App Control, check signatures before installing modules, forks and cores, and name any block clearly instead of failing: [../design/windows-smart-app-control.md](../design/windows-smart-app-control.md).
- A CI job under Microsoft's Smart App Control policy, a signature gate on every release, and a clean Windows 11 virtual machine for the real check.

**Owner first:** choose the certificate and its publisher name, and start identity validation, since it can take weeks. If it isn't ready in time, 0.6.3 ships the detection and messages, and signed builds follow in 0.6.4.

## 3D settings stay with the 3D disc

Full design: [../design/3d-settings-per-disc.md](../design/3d-settings-per-disc.md). The owner found the real cause of the stretched and shifted disc pictures: 3D viewing, chosen on a 3D Blu-ray with **Apply to: Everything**, was then applied to every disc and video, and nothing on screen said so. ## The server went down while playing music with lyrics: evidence first, then the fix

Full design: [../design/reliability-audit.md](../design/reliability-audit.md). The owner, 2026-11-02: "I was trying to play music, it was trying to download lyrics, and the full server crashed. yet, the logs show no evidence of what I experienced." The log has nothing between an update check at 14:26 and `shutting down` at 14:33; Windows recorded no crash, so it was most likely a hang. This is the one exception to "small" alongside Smart App Control:

- **Evidence that can't be lost:** stderr kept to a file from the first line; an in-memory flight recorder of the last 10 minutes at debug level (and Go's execution-trace flight recorder), written out on a bad stop, a hang or **Save what just happened**; a hang detector that dumps every goroutine's stack when the server stops answering; every outgoing call and child process logged.
- **Then reproduce it** on Windows with the owner's settings, and fix what's found.
- Open the reliability audit's milestone, with an issue per area.

## Logs that explain every stop

Full design: [../design/logging-improvements.md](../design/logging-improvements.md). The owner, 2026-11-02, after the server stopped: "can't find reason in UI logs". The log showed a clean stop with no reason, 27 seconds before the 0.6.1-alpha installer ran and failed. For 0.6.3-alpha, the small part:

- Every stop logs why (tray Quit, service stop, Windows shutdown, installer, update, signal, and so on) and what was running; every start says how the last run ended, and flags one that didn't stop cleanly.
- **Bug:** after a reset, `cache` and `cache\images` were missing and never recreated, so every thumbnail failed until a restart. Folders are created when written to.
- Support bundle: a `crashes/` note when there are none, a real `log.since`, and the logs from before a reset included or named.

## 1. One server at a time

Full design: [../design/single-instance.md](../design/single-instance.md).

Today a second copy fails on the port: the tray icon says **Stopped** with "address already in use" (from `docs/TROUBLESHOOTING.md`), which tells a beginner nothing about what to do. The plan:

- A second start of the same data folder is refused before it opens the database, and the person is asked:
  1. **Open the web UI** (the default, focused button), which opens the running server's address in the browser and exits.
  2. **Start another instance on another port**, which is only offered with a separate data folder (two servers on one database is how data gets damaged), and picks the next free port from 9798 up.
  3. **Exit.**
- The lock is per data folder, not per machine: a second data folder is a separate server and is allowed.
- Headless starts (service, Docker, `wittymediaserver serve` with no terminal) never ask: they print one clear line with the running server's address and exit with a distinct code.

**Done when:** a second double-click on Windows, macOS and Linux desktop shows the question; a second service start logs the line; two servers with two data folders run side by side; a crashed server's stale lock never blocks the next start. Tests on Linux first; the Windows dialog is for the owner to click, per the standing rule on native windows.
